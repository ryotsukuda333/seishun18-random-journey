# Requirements Document

## Introduction

本ドキュメントは、青春18切符ランダム旅行ジェネレーターの要求定義を記述する。本システムは、スマートフォンユーザーがワンタップで現在地から青春18切符で行けるランダムな目的地駅への経路を提案するウェブアプリケーションである。

**対象ユーザー**: スマホユーザー (iOS/Android/モダンブラウザ)
**利用シーン**: 休日のレジャー、即席のランダム旅行
**技術スタック**: React 18 + Vite (Frontend), Hono + Cloudflare Workers (API), Supabase (Database)

## Requirements

### Requirement 1: 位置情報取得と出発駅特定
**Objective:** スマホユーザーとして、現在地から最寄り駅を自動で特定したい。手動入力のフォールバックも利用できるようにしたい。

#### Acceptance Criteria
1. When ユーザーが「ランダム旅ボタン」を押下したとき、the システムは ブラウザ位置情報 API を呼び出し現在地座標を取得すること
2. When 位置情報の取得に成功したとき、the システムは HeartRails Express API を使用して最寄り駅を特定すること
3. If ユーザーが位置情報の利用を拒否したとき、then the システムは 駅名手入力 UI を表示し代替入力を促すこと
4. If 位置情報取得が技術的に失敗したとき (タイムアウト、API エラー等)、then the システムは エラーメッセージと駅名手入力 UI を表示すること
5. When ユーザーが駅名を手入力したとき、the システムは HeartRails Express API で駅名検索を実行し候補リストを表示すること
6. The システムは 位置情報を永続保存しないこと (プライバシー保護)

---

### Requirement 2: ランダム目的地駅の抽選
**Objective:** ユーザーとして、日本国内のランダムな駅を目的地として提案してほしい。抽選条件を指定して再抽選もできるようにしたい。

#### Acceptance Criteria
1. When 出発駅が確定したとき、the システムは 日本国内全域を対象にランダムな目的地駅を抽選すること
2. The システムは 抽選時に海上座標が選ばれた場合、最寄りの陸地駅にスナップすること
3. Where ユーザーが距離レンジを指定している場合、the システムは 出発駅からの概算距離でフィルタリングした駅から抽選すること
4. Where ユーザーが方角 (北/南/東/西) を指定している場合、the システムは 指定方角の駅のみを抽選対象とすること
5. Where ユーザーが除外都道府県を指定している場合、the システムは 指定都道府県の駅を抽選対象から除外すること
6. When ユーザーが「再抽選」ボタンを押下したとき、the システムは 同じ条件で別の目的地駅を抽選すること
7. The システムは 再抽選回数の上限 (例: 10回) を設け、超過時は上限到達メッセージを表示すること

---

### Requirement 3: 18きっぷ適合経路の取得と提示
**Objective:** ユーザーとして、青春18切符で利用可能な経路 (JR普通・快速のみ) のリンクを取得したい。

#### Acceptance Criteria
1. When 目的地駅が決定したとき、the システムは 乗換案内ジョルダン API を使用して出発駅から目的地駅への経路を検索すること
2. The システムは 検索条件として「JRのみ」「新幹線除外」「特急除外」を指定すること
3. When 経路検索が成功し、18きっぷ適合経路が見つかったとき、the システムは 経路詳細へのジョルダン外部リンクを表示すること
4. The システムは 経路リンクに加えて、概算の距離と所要時間を表示すること (ジョルダン API レスポンスから抽出)
5. If 18きっぷ適合経路が見つからなかったとき、then the システムは 「適合経路なし」メッセージと再抽選ボタンを表示すること
6. If 経路検索 API がエラーを返したとき、then the システムは エラーメッセージとリトライボタンを表示すること
7. The システムは ジョルダン API 利用規約に従い、クレジット表記と外部リンク必須要件を満たすこと

---

### Requirement 4: 検索結果の SNS 共有
**Objective:** ユーザーとして、旅行提案結果を SNS で簡単にシェアしたい。共有先でも魅力的に表示されるようにしたい。

#### Acceptance Criteria
1. When 経路リンクが表示されたとき、the システムは 「共有」ボタンを表示すること
2. When ユーザーが「共有」ボタンを押下したとき、the システムは Web Share API を呼び出し OS/ブラウザの共有 UI を起動すること
3. The システムは 共有テキストに「出発駅」「目的地駅」「経路リンク」を含めること
4. The システムは 共有用の短縮 URL を生成し、個人情報を含めないこと (匿名性担保)
5. The システムは 共有 URL ページに Open Graph Protocol (OGP) メタタグを設定すること
6. The OGP メタタグは タイトル、説明、サムネイル画像 (出発駅/目的地駅の情報を含むカード画像) を含むこと
7. If Web Share API が利用できない環境の場合、then the システムは クリップボードコピーボタンを代替として表示すること

---

### Requirement 5: エラー処理とユーザー誘導
**Objective:** ユーザーとして、エラーが発生しても次の行動が明確で、簡単にリトライや代替手段を試せるようにしたい。

#### Acceptance Criteria
1. If 位置情報拒否が発生したとき、then the システムは 「位置情報が必要です」メッセージと駅名手入力 UI を表示すること
2. If 駅が特定できなかったとき (複数候補あり、または該当なし)、then the システムは 候補駅リストまたは再取得ボタンを表示すること
3. If HeartRails Express API が障害を起こしたとき、then the システムは エラーメッセージと「時間をおいて再試行」案内を表示すること
4. If ジョルダン API が障害を起こしたとき、then the システムは エラーメッセージとリトライボタンを表示すること
5. If 目的地抽選が連続で失敗したとき (例: 5回連続で適合経路なし)、then the システムは 抽選条件の緩和を提案すること (距離レンジ拡大等)
6. The システムは すべてのエラーメッセージを平易な日本語で表示すること
7. The システムは エラー発生時も UI が破綻せず、ホームへ戻るボタンを常に表示すること

---

### Requirement 6: UI/UX とアクセシビリティ
**Objective:** スマホユーザーとして、直感的で使いやすいインターフェースを利用したい。アクセシビリティも確保されていてほしい。

#### Acceptance Criteria
1. The システムは LP のヒーロー部に「ランダム旅ボタン」を大きく配置すること
2. The システムは 抽選条件設定 UI を折りたたみ可能なセクションとして提供すること (初期状態は閉じている)
3. The システムは 検索結果をカード形式で表示し、出発駅/目的地駅/概算/外部リンク/共有ボタンを明瞭に配置すること
4. The システムは 色コントラスト比を WCAG AA 基準 (4.5:1 以上) で確保すること
5. The システムは すべてのインタラクティブ要素に適切な ARIA ラベルを設定すること
6. The システムは キーボード操作でのフォーカス移動が論理的順序であること
7. While ローディング中、the システムは スピナーまたはローディングメッセージを表示すること
8. The システムは モバイル優先のレスポンシブデザインを採用し、タブレット/PC でも適切に表示されること

---

### Requirement 7: パフォーマンスと可用性
**Objective:** ユーザーとして、スマホの 4G 回線でもストレスなく利用したい。システムが安定稼働していてほしい。

#### Acceptance Criteria
1. The システムは スマホ 4G 回線で Largest Contentful Paint (LCP) が 2.5 秒以内であること
2. The システムは First Input Delay (FID) が 100ms 以内であること
3. The システムは Cumulative Layout Shift (CLS) が 0.1 以下であること
4. The システムは 外部 API 呼び出しにタイムアウト設定 (例: 10秒) を設けること
5. The システムは 小規模アクセス (月間 1000 リクエスト程度) で安定稼働すること
6. The システムは 無料枠 (Cloudflare Workers, Supabase, 外部 API) 内で運用可能であること
7. If 無料枠を超過する兆候があるとき、then the システムは レート制限またはキャッシュで抑制すること

---

### Requirement 8: セキュリティとプライバシー
**Objective:** ユーザーとして、個人情報が安全に扱われ、外部に漏洩しないことを期待する。

#### Acceptance Criteria
1. The システムは 外部 API キー (HeartRails, ジョルダン) をクライアントに露出しないこと (サーバーサイドで管理)
2. The システムは すべての通信を HTTPS で暗号化すること
3. The システムは ユーザーの位置情報を永続保存しないこと
4. The システムは 共有 URL に個人特定情報を含めないこと (匿名性担保)
5. The システムは 外部 API へのリクエストに不要な個人情報を含めないこと
6. The システムは アクセスログとエラーログを最低限収集し、個人情報を含めないこと
7. The システムは Supabase の Row Level Security (RLS) を有効化し、データアクセス制御を行うこと

---

### Requirement 9: 運用とデプロイ
**Objective:** 開発チームとして、無料枠で安定稼働し、デプロイが容易なシステムを構築したい。

#### Acceptance Criteria
1. The システムは フロントエンドを Cloudflare Pages にデプロイすること
2. The システムは バックエンド API を Cloudflare Workers にデプロイすること
3. The システムは データベースを Supabase (本番環境) で運用すること
4. The システムは API キーを環境変数で管理し、リポジトリにコミットしないこと
5. The システムは デプロイパイプライン (例: GitHub Actions) を設定し、main ブランチへのマージで自動デプロイすること
6. The システムは エラーログを収集し、開発チームが確認できること (個人情報を含めない)
7. The システムは 外部 API の利用回数を監視し、無料枠超過前にアラートを発すること

---

## Non-Functional Requirements Summary

### パフォーマンス
- LCP < 2.5s (4G 環境)
- FID < 100ms
- CLS < 0.1

### 可用性
- 小規模アクセス (月間 1000 リクエスト) で安定稼働
- 外部 API 障害時のフォールバック (リトライ、エラーメッセージ)

### セキュリティ
- API キーのサーバーサイド管理
- HTTPS 通信
- 位置情報の非永続化
- 共有 URL の匿名性担保

### プライバシー
- 位置情報の最小限利用
- 個人情報の非保存
- ログの匿名化

### 運用コスト
- 無料枠内での運用 (Cloudflare, Supabase, 外部 API)
- レート制限とキャッシュによる超過防止

## External Dependencies

### HeartRails Express API
- **用途**: 駅情報取得 (最寄駅特定、駅名検索)
- **制約**: クレジット表記必須
- **エンドポイント**: 最寄駅検索、駅名検索

### 乗換案内ジョルダン オープン API
- **用途**: 経路検索 (18きっぷ適合経路)
- **制約**:
  - 外部リンク提示必須
  - 回数制限順守
  - アクセスキー管理
- **検索条件**: JRのみ、新幹線/特急除外

### Web Share API
- **用途**: SNS 共有機能
- **フォールバック**: クリップボードコピー (非対応環境)

## Acceptance Test Scenarios

### シナリオ 1: ハッピーパス (位置情報許可)
1. ユーザーが LP を開く
2. 「ランダム旅ボタン」を押下
3. 位置情報を許可
4. 最寄り駅が自動特定される
5. ランダム目的地駅が抽選される
6. 18きっぷ適合経路リンクが表示される
7. 「共有」ボタンで SNS シェアできる

**期待結果**: 1分以内に経路リンクが表示される

---

### シナリオ 2: 位置情報拒否 (手動入力)
1. ユーザーが LP を開く
2. 「ランダム旅ボタン」を押下
3. 位置情報を拒否
4. 駅名手入力 UI が表示される
5. 駅名を入力し候補から選択
6. ランダム目的地駅が抽選される
7. 18きっぷ適合経路リンクが表示される

**期待結果**: 手動入力でも同等の結果に到達できる

---

### シナリオ 3: 適合経路なし (再抽選)
1. ユーザーがシナリオ 1 を実行
2. 抽選された目的地駅に 18きっぷ適合経路が存在しない
3. 「適合経路なし」メッセージと再抽選ボタンが表示される
4. 「再抽選」ボタンを押下
5. 別の目的地駅が抽選される
6. 18きっぷ適合経路リンクが表示される

**期待結果**: 再抽選で適合経路が見つかる

---

### シナリオ 4: 外部 API 障害
1. ユーザーがシナリオ 1 を実行
2. ジョルダン API が障害中
3. エラーメッセージとリトライボタンが表示される
4. しばらく待機してリトライ
5. API が復旧し、経路リンクが表示される

**期待結果**: エラー時もユーザーが次の行動を取りやすい

---

### シナリオ 5: SNS 共有と OGP 表示
1. ユーザーがシナリオ 1 を実行
2. 「共有」ボタンを押下
3. Twitter に共有
4. Twitter カードに適切な OGP (タイトル、説明、サムネイル) が表示される

**期待結果**: 主要 SNS で想定通りの OGP が表示される

---

## Success Metrics (KPI)

- **旅生成成功率**: 外部経路リンク提示まで到達した割合 > 90%
- **再抽選回数**: 中央値 < 2 回
- **共有実行率**: 経路リンク表示後の共有ボタン押下率 > 20%
- **外部 API 失敗率**: HeartRails + ジョルダン合計 < 5%
- **リトライ成功率**: API 障害後のリトライ成功率 > 80%

---

## Risks and Mitigations

### リスク 1: 外部 API 制限/障害
**影響**: サービス利用不可
**対策**:
- キャッシュ戦略 (駅情報の一時保存)
- リトライロジック (エクスポネンシャルバックオフ)
- フォールバックメッセージ

### リスク 2: 18きっぷ適合経路の希少性
**影響**: 再抽選回数増加、ユーザー離脱
**対策**:
- 抽選ロジックのバリエーション追加 (距離/方角/地域バイアス)
- 適合率の高い地域優先抽選

### リスク 3: 無料枠超過
**影響**: コスト発生、サービス停止
**対策**:
- レート制限 (IP/ユーザーあたりのリクエスト上限)
- キャッシュ活用
- 使用量監視とアラート
